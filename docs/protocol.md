# Protocol reference

## Request headers

| Header | Required | Meaning |
| --- | --- | --- |
| `Fetch-Relay-Authorization` | Yes | `Bearer <RELAY_TOKEN>` authenticates the client to the Relay. |
| `Fetch-Relay-Target` | Yes | Complete absolute public `http:` or `https:` target URL. |
| `Authorization` | No | Ordinary upstream credential; forwarded to the target. |

The target is accepted only through `Fetch-Relay-Target`. Query-string and path
target formats are intentionally unsupported.

The Relay preserves the incoming ordinary HTTP method and body. It removes
Relay-control, hop-by-hop, forwarding-identity, origin/referrer, encoding, and
cookie headers before calling the target. `CONNECT` and `TRACE` return `405`.

## Response headers

| Header | Meaning |
| --- | --- |
| `Fetch-Relay-Request-ID` | Per-request UUID for correlating sanitized logs. |
| `Fetch-Relay-Location` | Original upstream redirect destination. |

Upstream `Location` and `Set-Cookie` are removed. CORS response headers are
generated by the Relay. Every response uses `Cache-Control: no-store`.

## Redirects

Upstream redirects are returned with their original 3xx status, but are never
followed by the Worker. The destination is moved from `Location` to
`Fetch-Relay-Location`. A client may validate that value and issue another
authenticated Relay request explicitly.

## Errors

Errors are JSON objects with a stable code and request ID:

```json
{
  "error": "unauthorized",
  "requestId": "0e72e66b-9af4-4ddb-82b2-7cbcf41302ae"
}
```

Common statuses are `400` for invalid targets, `401` for Relay authentication,
`405` for unsupported methods, `502` for upstream fetch failures, and `503`
when the Worker has no `RELAY_TOKEN` binding.

## Streaming and cancellation

The Worker passes `request.body`, `request.signal`, and `upstream.body` through
directly. It does not call `json()`, `text()`, or `arrayBuffer()` on application
bodies. This preserves SSE and binary streams and propagates client cancellation
to the upstream fetch.
